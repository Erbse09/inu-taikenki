Previewでは既存本番データを読むだけ。ここに保存したSQLをPreviewで適用するコマンドはない。

試験専用データは本番用SQLに含めない。既存IDと source_type/source_url を保つ。
適用前後に件数だけでなく既存行の内容・関連整合性を比較する。

## 口コミの検証可能性（2026-10-16 追加ルール）
サンプル調査（`audit/review-source-20261016/`）で、既存の公開レビュー要約のうち確認先ページで対応する投稿を確認できたのは約半数だった。
原因：`review_sources` テーブル（個別レビューの識別子用）は存在するが、既存データでは1件も登録されておらず、確認先の多くが「商品のレビュー一覧ページ」の共有URLだった。

今後の追加分は次を満たしてから公開承認に出す。
- 1行＝1つの識別できる投稿。確認先URLに加え、投稿日・投稿者表示名（ハッシュ化可）・一覧のページ番号・取得日を記録し、`review_sources` に追加する（追加のみ。既存行は更新しない）。
- 原文は保存しない。要約と、検証用に原文の短い指紋（ハッシュ）のみ。
- 要約は生成AIが作成した場合、その旨を作業記録（PR・Notion）に残す。
- 追加前に、無作為に10%以上を確認先ページで再確認し、結果をPRに書く。見つからないものは追加しない。
- 猫のレビューを犬の体験として登録しない（確認先で犬・猫のどちらかを必ず確認）。

## 出典IDの簡易方式（2026-11-25 運営者が承認）
対象：定期タスク「犬体験記｜毎日小記事」「犬体験記｜3日ごと本記事」。
背景：定期タスクの取得ツールは、レビュー本文を逐語（一字一句そのまま）で返さない。そのため、従来の `商品コード:投稿日:表示名ハッシュ8桁:本文の指紋10桁` のうち「本文の指紋」を作れず、2026-11-25の初回実行は0本で終わった。

本文の指紋を作れない場合に限り、次の簡易形式で `review_sources.source_review_id` を作ってよい。本文の指紋を作れるときは従来方式を優先する。

- 形式：`商品コード:投稿日(YYYYMMDD):表示名ハッシュ8桁:o注文日(YYYYMMDD。不明は o0):s星の数(1〜5)`
  - 例：`208747_10000923:20260423:1a2b3c4d:o20260420:s5`
  - 5区切りなので、従来形式（4区切り・末尾は16進10桁）とぶつからない。表示名は保存せず、ハッシュだけにする。
- 要約は、出典ページで実際に読めた本文だけを元にする。読めていない部分・推測で補わない。本文が途中までしか確認できない投稿は使わない。
- 原文（逐語）は、D1・リポジトリ・PR・Notionのどこにも保存しない。要約は自分の言葉で言い換える。
- 再確認（登録数の10%以上。小記事は最低3件）では、投稿日・星の数・表示名ハッシュ・注文日・内容の要点が出典ページと一致するかを見る。一致しないものは入れない。
- PRには、どの行が簡易方式（本文の指紋なし）かを明記する。サイト上の表示は従来どおり（`review_sources` に登録された行は「出典確認済み」）。
- 全文を逐語で扱える手段（取得ツール・手順）が用意できたら、運営者の承認を得てこの簡易方式をやめ、従来方式に戻す。
- 運営者はいつでもこの節を取り消せる。
